# Focus 独立软件能力设计

**类型：** 产品能力地图 / 架构边界决策
**日期：** 2026-07-08
**状态：** 方向确认，能力梳理
**背景：** Focus 模块从 UUUtil 孵化为独立软件，UUUtil 退化为其第一个客户端

---

## 1. 定位

一句话锁定，否则后面所有能力都会漂移：

> **它是一个"注意力/焦点引擎"，负责把散落在各种工具里的工作信号，自动归纳成可持续观察的焦点对象，并对外提供读写。**

它**不是** TODO 工具，**不是**聊天归档系统。重心是**摄取 + 归因 + 观察**，而不是"再做一个待办清单 UI"。这个定位决定了它值得从 UUUtil 独立出去——因为注意力引擎的适用场景远比一个桌面小工具广泛。

---

## 2. 架构边界决策（前置结论）

这是能力设计之前必须先钉死的地基。以下决策来自对当前实现的核实与逐步推演。

### 2.1 核实到的现实

- Focus 目前**并没有独立数据库**，它和白板、其他插件共用同一个 `.data/assistant.db`（sql.js 单库）。
- 当前 sql.js 采用"整库内存快照 + 整库覆盖落盘"模型，天然不支持多进程并发写，`reloadDatabaseIfChanged` / `saveToDisk` 基于 mtime 的机制会**静默丢写**。
- 因此"库间双向/单向同步"在当前架构下是伪命题——它们本来就是一个库。

### 2.2 定位升级如何改变技术选型

| 若 focus 只服务本机 UUUtil | 若 focus 服务广泛场景（多客户端 / 跨机 / 云） |
|---|---|
| 直接读文件 + WAL 最省 | 直接读文件失效，**必须 API 优先** |

一旦 focus 是"孵化出去、服务更广泛场景"的独立应用，它未来要面对多个客户端、可能跨机器、可能上云。文件共享（两个进程贴同一块磁盘）不具备扩展能力，因此边界必须是 **API**——这是唯一能同时服务"本机 UUUtil + 未来任意客户端"的边界。

### 2.3 锁定的边界

- **对外边界：API 优先**（HTTP 为主，后续可选 MCP / SDK / CLI）。
- **单一数据源：** focus 独占它自己的持久化，外部谁都不直接碰文件。
- **UUUtil 侧：瘦客户端 + 本地只读副本**。在线拉 API 并更新副本；focus 未启动 / 断网 / 云端不可达时，展示本地副本的上次数据（标注可能非最新）。副本**永远只读、永不回写**，因此不存在双向同步与冲突。
- **写（若保留）：** 走 API 命令下发，focus 独占写自己的库。
- **不再考虑共享文件 / 直接读文件**——它与"广泛服务"定位天然冲突。

### 2.4 关键原则

- **区分"真理之源"与"访问协调者"：** 数据（文件）永远在磁盘上、不依赖任何进程存活；只有写与多写者协调才需要服务进程。读的可用性应由"数据在不在"决定，而不是"进程活没活"决定——本地只读副本正是为此兜底。
- **CQRS 视角：** 读远多于写。读走本地副本 / API，不依赖写者在线；写才走 API 协调。
- **心态转变：** focus 是独立产品，UUUtil 只是它的第一个 reference client。API 按"服务任意客户端"设计，不能夹带 UUUtil 私货，否则接第二个消费者时要推倒重来。

## 3. 能力地图

### 3.1 摄取层（数据从哪来）

区别于普通笔记软件的根本能力。

- **多入口接收：** HTTP webhook、MCP、CLI、SDK，任何工具都能投递事件。
- **标准事件协议：** 定义统一的"注意力事件（Attention Event）"格式，各来源（Claude Code、Codex、Cursor、Git hook、终端、CI）只负责翻译成该格式。**协议是核心资产，适配器是外围。**
- **幂等：** 同一事件重复投递（hook 重试、网络重发）不重复写焦点，靠 `来源 + 事件ID` 去重。
- **Hook 驱动而非自觉驱动：** 可靠性来自系统级触发，不依赖 AI 记得调用。这是独立孵化的最大理由。

### 3.2 提取与归因层（大脑）

- **实质性判断：** 过滤寒暄、无结论浏览，只留真正的进展 / 决策 / 阻塞。
- **主题提取：** 从文件路径、项目名、commit message、对话摘要提炼焦点候选。
- **焦点匹配：** 判断信号是"延续已有焦点"还是"形成新焦点"。
- **决策引擎：** 输出明确动作——跳过 / 记 check-in / 新建焦点 / 修正元数据 / 低置信度待人工确认。
- **规则优先、LLM 兜底：** 先跑便宜的规则，搞不定或长对话再上模型，成本可控。
- **可解释：** 每个归因留下"为什么这么判"的理由，便于纠错和建立信任。

### 3.3 焦点建模层（世界观）

当前 focus 模块已有雏形，值得保留并强化。

- **焦点不是任务：** 无"完成"状态，用**权重、注意力模式（deep/pulse/scan/dormant）、健康度（aligned/drifting/neglected/cooling）、衰减、异动告警**表达注意力状态。
- **时间衰减：** 长期不检视的焦点自动降权、淡出，模拟真实注意力流失。
- **check-in 记录：** 每次关注留痕（能量、阻塞、下一步）。
- **异动检测：** 低权重却频繁检视、长期忽略、自然淡出等，主动给信号。
- **标签 / 分类体系：** 焦点的横向组织维度。

### 3.4 存储层

- **独占持久化：** 自己拥有数据库（SQLite 起步，预留迁 Postgres 空间），外部不直接碰文件。
- **原始事件与归因结果分离：** 事件表（可回放）、归因运行记录表（审计）、焦点表、check-in 表、链接表。
- **可回放：** 保留摄取过程，以便调参后重新归因、复盘误判。

### 3.5 对外接口层（怎么被用）

按"服务任意客户端"设计。

- **读接口：** 焦点列表、单焦点详情、check-in 历史、统计、告警、待确认项。
- **写 / 命令接口：** 摄取事件、人工新建 / 修正焦点、确认或纠正低置信度归因。
- **多协议：** HTTP API（主）、MCP（给 AI）、CLI（给 hook 和调试）、SDK（给集成方）。
- **变更通知：** 客户端要能感知"数据变了"，不能只靠轮询。需要订阅 / 推送（SSE、webhook 回调、或版本号轮询）——直接支撑 UUUtil 本地只读副本的更新。

### 3.6 消费与查询层（读侧要富）

未来记忆库、任务总览、日程总览都要读它，读侧要比写侧更丰富。

- **多视角查询：** 按时间、项目、标签、健康度、注意力分布切。
- **派生视图：** 允许消费者按需投影（如任务总览把某类焦点当任务看），但**派生数据存在消费者侧，不回写**。
- **稳定读契约：** 对外读结构稳定（视图 / DTO 层），内部表怎么重构都不破坏客户端。

### 3.7 隐私与安全层（必须前置）

处理对话和工作上下文，隐私不能后补。

- **分级隐私模式：** 只存元数据 / 只存摘要 / 存脱敏片段 / 存原文，用户可选，默认"只存摘要"。
- **脱敏：** 自动过滤 API Key、Token、私钥、.env、大附件、base64。
- **访问边界：** 本地服务默认只听 `127.0.0.1`；远程访问必须带 token / mTLS；webhook 入口签名校验。
- **LLM 隔离：** 提取器默认不喂原文，除非用户显式授权。

### 3.8 可靠性与可观测层（它是常驻服务）

- **幂等 + 重试 + 死信：** 摄取失败可重试，反复失败进死信而不丢。
- **结构化日志：** 每次摄取、归因、决策、同步留痕（JSON Lines），不记敏感原文。
- **健康检查：** `/health` 端点，客户端可探活。
- **审计：** 任何创建、合并、修正可追溯到来源和理由。
- **优雅关闭：** 退出前落盘待写数据。

### 3.9 生命周期与部署层

- **多形态部署：** 本地 daemon（个人）→ 可选 Docker → 可选云端（团队），同一套核心不同壳。
- **进程生命周期：** 能被客户端按需拉起、开机自启，让"服务存活"对用户隐形。
- **数据迁移：** 从 UUUtil 现有 focus 表迁出的一次性通道 + 后续 schema 版本管理。

### 3.10 扩展层（决定能走多远）

- **适配器机制：** 接新工具 = 写个把事件翻译成标准协议的适配器，不动核心。
- **提取器 / 匹配器可插拔：** 规则版、LLM 版、未来向量版可替换升级，且带版本号（便于回放对比）。
- **多客户端友好：** UUUtil 只是第一个客户端，API 不能有私货。

---

## 4. 优先级取舍

全做会失焦，建议排序：

**必须先有（证明核心假设）：**
标准事件协议 + 摄取入口 + 幂等 + 规则归因 + 焦点建模（现有这套）+ 读写 API + 结构化日志。

**紧接着：**
变更通知（支撑客户端副本）+ 隐私脱敏 + MCP 接口 + CLI / hook。

**可后置：**
LLM 提取、Web 管理台、云 / 团队、向量检索、多租户权限。

---

## 5. 结论

- 这个软件的护城河**不在 UI**，而在 **"标准事件协议 + 可靠摄取 + 可解释归因"** 这三样。
- 先把从 **hook → 焦点** 的闭环跑稳，其它能力都围绕它生长。
- UUUtil 只需守住一条线：**它是客户端，不是数据主人。**
