# 知识库改造方案

## 一、现状分析

### 1.1 当前实现

当前知识库插件已实现基础功能：
- 笔记的增删改查
- 分类管理
- 标签管理
- 简单模糊搜索

代码结构：
- 插件主入口：`src/plugins/knowledge-base/index.ts`
- API 实现：`src/plugins/knowledge-base/api.ts`
- 前端界面：`renderer/components/KnowledgeBase.tsx`
- 数据库表：`kb_categories`、`kb_tags`、`kb_notes`、`kb_note_tags`

### 1.2 存在的问题

| 问题类别 | 具体描述 | 影响 | 是否根本性问题 |
|----------|----------|------|----------------|
| **空间错配** | UUUtil 是右侧抽屉（~800px），但当前三栏布局（分类+列表+空区域）非常拥挤 | 可利用空间不足，阅读编辑体验差 | ✅ 是 |
| **交互错位** | 设计理念是"编辑优先"，点击卡片直接进入全屏编辑，但实际用户大部分时间在**浏览查找** | 找笔记麻烦，操作路径长 | ✅ 是 |
| **搜索简陋** | 只用 `LIKE %keyword%`，不支持分词，没有权重，只能按时间排序 | 找不到想要的笔记，搜索价值低 | ✅ 是 |
| **缺少特性** | 无笔记预览、无星标收藏、无虚拟滚动 | 重要笔记不突出，笔记多了可能卡顿 | ⚠️ 是 |
| **操作低效** | 添加分类/标签层级太深，需要多次点击 | 编辑笔记时添加标签麻烦 | ⚠️ 是 |

### 1.3 结论

> **知识库存在根本性架构问题，增量改进无法解决，必须重做。**

- 数据库 schema 设计合理，可以兼容复用，**不需要数据迁移**
- 插件 API 可以逐步重构，工作量可控
- 核心问题是交互布局和信息架构，不是数据结构

## 二、产品定位

### 2.1 核心定位

**快速记录临时想法、沉淀可复用知识碎片的本地笔记工具箱**

- 不替代 Notion/Obsidian 等专业笔记软件
- 优势：和开发工作流集成，随用随开，无需切换应用
- 核心价值：**快速找到你记过的东西**

### 2.2 关键使用场景

1. **快速记录**：记下一时想不清的问题，后续慢慢思考
2. **知识沉淀**：沉淀解决过的技术问题，避免重复踩坑
3. **代码收集**：收集有用的代码片段、配置模板
4. **思路整理**：整理想法和思路，比白板更持久

### 2.3 设计原则

1. **适配窄面板**：承认宽度只有 ~800px，做分栏布局而非全屏切换
2. **浏览优先**：打开就能看到列表 + 预览，编辑是次一级操作
3. **搜索高效**：默认列表 + 搜索结果一体化，输入即搜索
4. **简化操作**：分类/标签添加不要嵌套太深，点击就能加
5. **兼容现有数据**：数据库 schema 保持向后兼容

## 四、交互设计

### 4.1 整体布局

新布局采用**四区域弹性布局**，适配 800px 窄面板：

```
┌─────────────────────────────────────┐
│ 🔍 搜索框 筛选 【折叠按钮】 新建笔记   │  ← 顶部操作栏（高度固定）
├──────────┬────────────────────────────┤
│ 分类/标签 │         笔记列表            │  ← 左侧边栏（可折叠）
│ (可折叠) │  - 标题 + 摘要 + 星标        │
│          │  - 按更新时间倒序           │
├──────────┼───────────┬─────────────────┤
│          │ 编辑区    │    预览区        │  ← 双栏编辑预览区
│          │ (Markdown│  (实时渲染)      │
│          │  输入)    │                 │
│          │           │                 │
┴──────────┴───────────┴─────────────────┘
```

**布局比例**：
- 侧边栏（分类/标签）：固定宽度 180px，可折叠（折叠后 0px）
- 笔记列表：宽度占剩余空间的 1/3（约 200px），列表模式可见
- 编辑+预览：宽度占剩余空间的 2/3（约 400px）
- 在列表模式下：笔记列表占满右半区域（没有编辑预览区）
- 在编辑模式下：笔记列表保留，右侧分出编辑+预览双栏

### 4.2 交互流程

**当前流程（编辑优先，不好）**：
```
打开 → 看到分类+笔记卡片网格 → 点击卡片 → 进入全屏编辑
```

**新流程（浏览优先，更好）**：
```
打开 → 看到【侧边栏 + 笔记列表 + 选中笔记预览】
               ↓
点击笔记 → 右侧预览更新，保持浏览状态
               ↓
点击"编辑" → 进入双栏编辑模式，左侧编辑右侧预览
               ↓
保存 → 返回预览状态
```

### 4.3 核心交互细节

#### 笔记列表

- 每条笔记展示：**星标按钮 + 标题 + 摘要 + 分类 + 标签 + 更新时间**
- 摘要自动取内容前 100 字
- 星标笔记置顶排序
- 鼠标悬停显示操作按钮（编辑/删除）

#### 搜索筛选

- 顶部搜索框，**输入即搜索**，实时更新列表
- 搜索权重：标题匹配 > 内容匹配
- 支持组合筛选：`分类 AND 标签 AND 关键词`
- 筛选条件都展示在搜索框后方，可一键清除

#### 双栏编辑

- 左侧：Markdown 编辑器
- 右侧：实时渲染预览
- 滚动不同步（编辑区滚动不需要预览区跟着滚）
- 保存快捷键：`Ctrl/Cmd + S`
- 取消快捷键：`Esc`

#### 侧边栏折叠

- 侧边栏（分类+标签）提供折叠按钮
- 折叠后，笔记列表和编辑预览区可以占满整宽度
- 适合专注编辑笔记时使用

## 五、数据层改进

### 5.1 数据库变更

当前 schema：

```sql
-- 已有表保持不变
kb_categories
kb_tags
kb_notes
kb_note_tags
```

新增字段：

```sql
-- kb_notes 表新增 star 字段
ALTER TABLE kb_notes ADD COLUMN star INTEGER DEFAULT 0;
-- 0 = 未星标，1 = 已星标
```

新增 FTS5 全文索引表：

```sql
-- 使用 SQLite FTS5 做全文搜索，支持中文分词
CREATE VIRTUAL TABLE IF NOT EXISTS kb_notes_fts
USING FTS5(title, content, note_id);
```

**触发器**：在笔记插入/更新/删除时自动同步 FTS 表

### 5.2 搜索改进

**现有搜索**：
```sql
SELECT * FROM kb_notes
 WHERE title LIKE '%xxx%' OR content LIKE '%xxx%'
 ORDER BY updated_at DESC
```

**改进后搜索**：
```sql
-- 使用 FTS5 全文搜索，按相关性排序
SELECT n.*, snippet(kb_notes_fts)
  FROM kb_notes_fts
  JOIN kb_notes n ON n.id = kb_notes_fts.note_id
 WHERE kb_notes_fts MATCH ?
 ORDER BY rank
```

优点：
- 支持中文分词搜索
- 按相关度排序而不是时间排序
- 搜索速度比 LIKE 快很多

### 5.3 API 变更

| API | 变更 |
|-----|------|
| `createNote` | 新增 `star` 参数，默认 0 |
| `updateNote` | 新增 `star` 参数 |
| `toggleStar` | **新增** - 切换笔记星标状态 |
| `getNotes` | 排序规则改为：星标降序 → 更新时间降序 |
| `searchNotes` | 改用 FTS5 搜索，按相关度排序，支持筛选组合 |

## 六、非功能需求

1. **性能**：
   - 笔记列表虚拟滚动，保证 500+ 笔记流畅
   - FTS5 搜索响应时间 < 100ms

2. **兼容性**：
   - 现有数据平滑升级，不需要迁移
   - 首次打开自动创建 FTS 表并同步数据

3. **可访问性**：
   - 所有操作支持键盘快捷键
   - 色彩对比度符合 WCAG 标准

4. **隐私**：
   - 所有数据本地存储，不上传
   - 支持一键清空所有笔记

## 八、风险与依赖

### 风险

1. **SQLite FTS5 中文分词**：SQLite 本身不带中文分词，需要检查 sql.js 是否支持。如果不支持，可以先继续用 LIKE + 简单分词排序，不影响整体架构。
2. **虚拟滚动依赖**：需要评估现有依赖是否有合适的虚拟滚动组件，或者手动实现简单版。

### 依赖

- 项目已使用 Chakra UI + React，保持一致
- sql.js 支持扩展和 ALTER TABLE，已有数据库可以正常升级
- FTS5 是 SQLite 3 核心功能，sql.js 默认编译已包含

---

## 九、总结

- 当前知识库存在根本性交互布局问题，必须重做
- 数据层兼容，可以复用现有 schema，只做增量扩展
- 核心改进：从"编辑优先"改为"浏览优先"，适配窄面板，提升搜索体验
- 分阶段开发，先完成核心必须功能，再逐步优化体验
