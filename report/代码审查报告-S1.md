### 1.2 核心数据流

- **启动顺序**（`src/main/index.ts:47`）：`initLogger → initDatabase → initAi → loadAllPlugins → bus.emit('core:ready') → registerAllIpc → startCliServer → createBallWindow/Tray/快捷键`。顺序正确，插件在 `core:ready` 后建表。
- **渲染 → 业务**：`window.assistant.*` → preload `ipcRenderer.invoke` → `ipc/*.ipc.ts` handler →（a）直接调 `core/*`，或（b）直接 import 插件 `api.ts`，或（c）`bus.emit` 请求/响应。
- **外部工具 → 业务**：`uuutil` CLI → loopback HTTP `127.0.0.1:17878`（`cli-server.ts`）→ `invokeCommand` → command-registry → 插件注册的 handler。
- **持久化**：所有写操作 → `getDatabase().run()` → `autoSave()`（500ms debounce）→ `db.export()` 全量写 `assistant.db`。带 mtime 冲突检测（外部改动则跳过覆盖）。

## 三、技术债务清单（按严重度排序）

### 🔴 3.1 [严重·功能性 bug] reminder Agent waiter 机制完全失效

`src/plugins/reminder/api.ts` 中 `_setAgentWaiter`（599 行）、`agentUpdate`（502 行）、`agentClose`（578 行）内部**每次都 `new Map()` 新建一个空 Map** 来注册/查找/删除 waiter，而不是复用对象上持久的 `this._agentWaiters`（448 行定义但从未被真正使用）：

```ts
// api.ts:599  注册 waiter —— 存进一个当场丢弃的空 Map
_setAgentWaiter(topic, resolveFn, timeoutMs) {
  const existing = new Map().get(topic);      // 永远 undefined
  ...
  new Map().set(topic, { resolve: resolveFn, timer });  // 存进即丢
}
// api.ts:502  agentUpdate 唤醒 waiter —— 也是空 Map
const waiter = new Map().get(input.topic);    // 永远 undefined
```

**失败场景**：Agent 通过 CLI 调 `agent.wait`（`index.ts:262`）→ handler 走 `new Promise(resolve => api._setAgentWaiter(...))`。由于 waiter 注册进了被丢弃的临时 Map，用户在面板响应（`agentUpdate` 更新）或 `agentClose` 时**无法唤醒该 Promise**，`agent.wait` 只能等到 setTimeout 超时（默认 300s）返回 `null`。→ Agent 阻塞式交互（skill `uuutil-reminder` 的 wait 语义）实际上永远拿不到用户的实时响应。

**修复方向**：将三处 `new Map()` 全部替换为 `this._agentWaiters`（或模块级单例 Map）。同时 `agent.wait` 唤醒目前只依赖 `agentUpdate`/`agentClose`，而面板响应走的是 `reminderApi.respond → fulfillWaiter`（`waiters.ts`，针对 reminder.ask 的 id），两套 waiter 未打通——Agent 提醒被面板 respond 后也不会触发 `_agentWaiters`。需统一唤醒路径。

### 🟠 3.2 [架构合规] reminder 的 agentUpdate 未走 waiters.ts，与 ask 的 waiter 体系割裂

`reminder.ask` 用 `waiters.ts`（模块级持久 Map，设计正确）；Agent 模式却另起 `_agentWaiters` 且实现错误（见 3.1）。两套阻塞等待机制并存、语义重叠但互不联通，是重复设计。建议统一为一套 topic/id 皆可索引的 waiter 表。

### 🟠 3.3 [架构合规] IPC 层直接 import 插件 api.ts，绕过 bus

`src/main/ipc/reminder.ipc.ts:9` `import { api as reminderApi } from '../../plugins/reminder/api'`，`focus.ipc.ts` 同理。CLAUDE.md 铁律 1 要求"跨模块通信必须走 bus"，铁律 2 允许"api.ts 是唯一合法对外接口"。当前做法**踩在两条铁律的边界上**：直接 import api.ts 虽比 import 内部实现好，但绕过了 EventBus，使插件与主进程强耦合（如 reminder 插件删除即导致 IPC 编译失败）。属于有意折中，但应在 CONVENTIONS 中显式记录该例外，否则规则形同虚设。

### 🟡 3.4 [功能缺口] 插件 enabled 字段写入但从不读取

`db.ts:50` `_plugins` 表有 `enabled` 列，`plugin-loader.ts:90` 每次加载写入 `enabled=1`，但加载逻辑（`loadAllPlugins`）**无条件加载所有目录**，从不查询 enabled。→ 无法禁用插件；`_plugins` 表的 enabled 语义是死数据。

### 🟡 3.5 [性能] 数据库全量 export 落盘

`db.ts:125` 每次 `autoSave` 触发 `db.export()` 序列化**整个数据库**再全量写盘。随笔记/提醒/事件日志增长，单次落盘成本线性上升。`_events_log`（calculator/dev-utils 每次操作都写）无清理机制，会无限增长。建议：为 `_events_log` 加保留窗口/清理任务；大数据量时评估增量方案或改用真实 sqlite 驱动。

### 🟡 3.6 [代码质量] reminder/api.ts 内联 IIFE 严重重复

`agentUpdate`/`agentClose`/`agentQuery` 中"按 topic 查最新一条"的 `selectRows(...).map(mapRow)` 逻辑以匿名 IIFE 形式**复制了 6+ 次**（如 452、504、517、542、561、582 行）。应提取为 `findLatestByTopic(topic)` 单一函数。`mapRow`（`api.ts:150`）对 `row[19]` 调 `parseJsonObject` 两次，小幅冗余。

### 🟡 3.7 [调试残留] main/index.ts 生产 console.log

`src/main/index.ts:69-99` bootstrap 里保留了 `console.log('=== 开始创建窗口和托盘 ===')` 等中文调试输出，与统一日志框架并行。建议清理或降级为 `logInfo`。

### ⚪ 3.8 [其他]

- **无自动化测试**：全项目零测试。个人工具项目可接受，但 reminder（含 3.1 bug）、db 冲突检测、command-registry 超时等核心逻辑缺少回归保护——3.1 这类 bug 正是测试缺位的直接后果。
- **hello-world 示例插件在生产加载**（§2.2），暴露 `hello-world.greet` CLI 命令。
- **CLI server 无鉴权**：`cli-server.ts` 仅绑 `127.0.0.1`，本机自用可接受；但 terminal 是无过滤的完整 shell（`terminal.ts:5` 已警示），须确保该能力永不经 CLI/命令表暴露——目前 terminal 走 IPC 不走 command-registry，合规。

## 五、插件化架构完整度与合规性评估

| CLAUDE.md 铁律 | 合规度 | 说明 |
|----------------|--------|------|
| 1. 插件间禁止直接 import，走 bus | 🟢 达标 | 插件之间确无互相 import；calculator/kb/dev-utils 均经 bus |
| 2. 插件对外唯一接口 api.ts | 🟡 部分 | 插件对外确经 api.ts；但**主进程 IPC 直接 import api.ts 绕过 bus**（§3.3），属边界折中 |
| 3. DB 统一入口 + 写后 autoSave | 🟢 达标 | 全部经 `getDatabase()`，写后 `autoSave()`/事务封装（kb 有 runInTransaction） |
| 4. 事件命名空间 core:*/plugin-id:* | 🟢 达标 | `event-map.ts` 类型化约束，命名规范 |
| 5. handler 不抛异常 | 🟢 达标 | EventBus 静默捕获；command-registry 永不抛出 |
| 6. 日志统一入口 + 脱敏 | 🟢 达标 | 主/核心用 core/logger，渲染用 window.assistant.log；脱敏靠调用方自觉（无强制过滤） |

**完整度评价**：插件化骨架**成熟且自洽**——manifest/activate/deactivate 生命周期、bus 通信、command-registry（CLI 出口）、api.ts 契约、类型化事件映射一应俱全，新插件复制 hello-world 即可接入。**主要缺口**：(a) enabled 开关未实装（§3.4），插件无法动态启停；(b) IPC 与插件的耦合点（§3.3）应显式记录为架构例外；(c) reminder 的 Agent waiter 实现（§3.1）是插件层最薄弱环节。

## 六、总体结论与建议

1. **内核层健壮**，架构分层清晰、职责单一，可作为后续开发的稳固地基。
2. **首要修复项**：§3.1 reminder Agent waiter bug（`new Map()` 误用）——这是当前唯一影响功能正确性的**确凿严重 bug**，且直接削弱了 `uuutil-reminder` skill 的核心价值（阻塞式 wait）。既有报告称 reminder"功能完整、无已知严重 bug"的判断**需修正**。
3. **既有报告与代码的偏差**：`功能整理` 报告将 reminder/knowledge-base 标为"✅ 完成"，但 (a) reminder Agent wait 实际失效，(b) 知识库改造方案（star/FTS/双栏）未落地。后续开发前应以本报告为准校正基线。
4. **建议动作优先级**：修复 3.1 → 提取 3.6 重复代码 → 补 reminder 核心逻辑最小测试 → 落实 3.4 enabled 或删除死字段 → 清理 3.7 调试输出 → 分主题提交当前 8 个未提交变更。
