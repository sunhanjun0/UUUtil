> 编制角色：规则约束管理
> 编制日期：2026-07-27
> 适用范围：`src/`（core / main / plugins / cli / shared）、`renderer/`、构建配置
> 定位：本文是 `docs/CONVENTIONS.md`（铁律与命名约定）的**落地补充**，聚焦编码规范、插件模板、Git 工作流、评审清单与 EventBus 检查。团队规模小，规则从简，可执行优先，拒绝形式主义。

规则分级说明：
- **【必须】** — 违反即视为缺陷，评审必须打回。
- **【推荐】** — 默认遵守，有充分理由可豁免，需在 PR/提交说明中注明。
- **【禁忌】** — 明确禁止的高风险做法。

## 一、编码规范

### 1.1 命名（沿用 CONVENTIONS.md，此处补充边界）

| 类型 | 规范 | 示例 | 级别 |
|------|------|------|------|
| 插件目录 / 插件 id | 全小写横线分隔 | `knowledge-base` | 【必须】 |
| TS 文件 | 全小写横线或点分隔 | `event-bus.ts`、`ai.ipc.ts` | 【必须】 |
| React 组件文件与导出 | PascalCase | `ReminderCenter.tsx` | 【必须】 |
| 数据库表名 | 蛇形 + 插件前缀 | `plugin_reminder_items`、`kb_notes` | 【必须】 |
| 数据库列名 | 蛇形，JSON 列以 `_json` 结尾 | `created_at`、`metadata_json` | 【必须】 |
| bus 事件名 | `plugin-id:action`（冒号） | `reminder:changed` | 【必须】 |
| CLI 命令 id | `plugin.action`（点号） | `reminder.notify` | 【必须】 |
| 布尔变量/函数 | `is/has/should` 前缀 | `isActive`、`hasResponse` | 【推荐】 |
| 常量 | UPPER_SNAKE_CASE | `DEFAULT_ASK_TIMEOUT_SEC` | 【推荐】 |

- 【必须】数据库表名前缀不一致是历史遗留（`kb_*` vs `plugin_reminder_*`）。**新插件一律用 `plugin_<id>_<entity>` 前缀**，老表不强制迁移。
- 【禁忌】用拼音、缩写歧义命名（如 `rmd`、`kbn`）。

### 1.2 注释

- 【必须】每个文件顶部有一段块注释，说明**职责**与**铁律约束**（现有插件均已遵守，如 `api.ts` 顶部的"唯一合法入口"声明，保持）。
- 【推荐】注释解释**为什么**而非**做什么**；代码能自解释的不写注释。
- 【推荐】临时妥协/已知坑用 `// TODO(原因)` 或 `// FIXME(bug编号)` 标注，便于检索。
- 【禁忌】保留大段被注释掉的死代码，交给 git 记录。

### 1.3 模块组织

- 【必须】三配置边界不可越界：
  - 渲染进程（`renderer/`）只经 `window.assistant.*` 通信，**禁止** import `src/main/` 或 `src/core/`、`src/plugins/`。
  - 主进程（`src/main/`）可 import `core/*` 与插件 `api.ts`，**禁止** import 渲染代码。
  - `tsconfig.json`（渲染+core+shared，ESNext）与 `tsconfig.main.json`（主进程，commonjs）的 include/exclude 边界不得混淆。
- 【必须】跨模块类型统一放 `src/shared/types.ts`；`window.assistant` 类型合同统一维护在 `src/shared/assistant-api.ts`（preload 改签名必须同步）。
- 【推荐】单文件超过 ~500 行或职责超过 2 个时拆分（参考 `reminder/` 拆出 `waiters.ts`）。

### 1.4 错误处理（补充 CONVENTIONS.md）

- 【必须】EventBus handler 内部异常自行 try/catch，绝不外抛（外抛会被静默吞掉，等于丢失）。已由 `event-bus.ts` 兜底并记日志，但**插件仍应主动处理并记录摘要**，不要依赖兜底。
- 【必须】CLI 命令 handler 通过抛 `Error` 表达失败，由 `command-registry` 统一转 `{ ok:false, error }`；不要自己拼错误结构。
- 【必须】IPC 边界返回明确的 `{ success, error }` 或业务结构，不把未捕获异常直接抛给 UI。
- 【禁忌】`catch {}` 空吞异常且不记日志（`dev-utils/index.ts:38` 的 `// 忽略` 是反例，新代码不允许）。

### 1.5 数据库与持久化（补充 CONVENTIONS.md）

- 【必须】所有写操作后调用 `autoSave()`；读多写少场景不要漏调。
- 【必须】`stmt.prepare()` 后必须在 `finally` 中 `stmt.free()`（参考 `reminder/api.ts` 的 `selectRows`）。
- 【必须】SQL 参数绑定禁止传 `undefined`（sql.js 会抛 bind 错误）——统一 `?? null` 兜底。**这是已发生过两次的真实缺陷**（见 git `fd1e866`/`d2a3f59`），新增字段务必检查。
- 【推荐】建表用 `CREATE TABLE IF NOT EXISTS` + 独立 `CREATE INDEX IF NOT EXISTS`；老库加列用 `try { ALTER TABLE ... } catch {}`（sql.js 无 `ADD COLUMN IF NOT EXISTS`）。
- 【禁忌】外部进程绕过主进程直接长期写 `.data/assistant.db`；跨进程接入走 CLI / IPC 入口。

### 1.6 日志与安全（沿用 CONVENTIONS.md 铁律，强调红线）

- 【禁忌】记录 API Key、Token、完整请求头、完整用户输入、附件正文、base64、dataUrl。
- 【必须】日志走统一入口：主进程/核心用 `core/logger`，渲染进程用 `window.assistant.log()`。
- 【推荐】`message` 用稳定可搜索的动作名（如 `chat_stream_completed`），`meta` 只放诊断字段（耗时、finishReason、资源 id）。

## 二、插件开发模板与规范

### 2.1 标准骨架

复制 `src/plugins/hello-world/`，一个插件目录固定包含：

```
src/plugins/<plugin-id>/
├── index.ts   # manifest + activate() + deactivate()
├── api.ts     # 对外唯一合法接口（类型定义在 shared/types.ts）
└── *.ts       # 可选内部实现（禁止被外部 import）
```

### 2.2 强制清单（新插件评审对照）

- 【必须】`index.ts` 导出 `manifest`（id/name/version/description）、`activate`、`deactivate`。
- 【必须】需要建表的插件在 `bus.on('core:ready', ...)` 内建表，**不要在模块顶层或 activate 同步阶段访问数据库**（DB 尚未 ready）。
- 【必须】对外能力只经两条合法出口：
  - `api.ts` 导出的 API 对象（供主进程 import）；
  - `registerCommand()` 声明的 CLI 命令（供外部工具）。
- 【必须】CLI 命令 id 用 `plugin.action` 点号；bus 事件用 `plugin-id:action` 冒号；两者命名空间不得混用。
- 【必须】`activate()` 结尾 `bus.emit('<id>:activated', { version })`，`deactivate()` 发 `<id>:deactivated`（保持全插件一致，便于观测）。
- 【必须】新增 bus 事件先在 `src/shared/event-map.ts` 的 `AppEventMap` 登记类型，否则 `bus.emit/on` 失去类型保护。
- 【推荐】CLI 命令带 `params`（含 required/description）与 `example`，`list`/`help` 自动展示；阻塞式命令显式设 `timeoutMs`。
- 【禁忌】插件之间直接 `import`（含 import 别的插件 `api.ts`）——所有跨插件通信走 `bus`。
- 【禁忌】把示例插件（hello-world）当真实功能长期挂在生产加载（S1 BUG-4，应在 plugin-loader 层排除或用 enabled 关闭）。

### 2.3 两种交互范式选择

| 范式 | 适用 | 代表 |
|------|------|------|
| **事件式**（`bus.on('x:do')`→ 处理 → `bus.emit('x:result')`） | 渲染进程触发、无需返回值配对 | calculator、knowledge-base |
| **命令式**（`registerCommand` handler 直接 return） | 外部工具一问一答、需请求/响应配对 | reminder、focus |

- 【推荐】新插件优先命令式（类型清晰、天然请求响应、自动进 CLI）；纯 UI 内部交互可用事件式。

## 三、Git 分支策略与提交规范

### 3.1 分支（小团队轻量流）

- 【必须】`main` 为唯一长期分支，保持可构建（`npm run build` 通过）。
- 【推荐】功能/修复走短生命周期分支：`feat/<简述>`、`fix/<简述>`、`docs/<简述>`、`refactor/<简述>`，合并后删除。
- 【推荐】阶段性大改造可用 `feat/<模块>-s<阶段号>`（呼应现有 S1–S4 阶段划分）。
- 【禁忌】在 `main` 上直接堆积破坏构建的半成品提交。

### 3.2 提交信息（Conventional Commits，项目已在用）

格式：`<type>(<scope>): <中文简述>`，与现有 git 历史一致。

- 【必须】`type` ∈ `feat` / `fix` / `docs` / `refactor` / `style` / `test` / `chore` / `perf`。
- 【必须】`scope` 用模块名：`reminder`、`focus`、`terminal`、`cli`、`ai`、`window`、`main`、`skill` 等。
- 【推荐】一次提交只做一件事；修 bug 的提交在正文引用缺陷来源（如 `BUG-1` 或复现说明）。
- 【推荐】示例（取自现有历史，风格保持）：
  - `feat(reminder): Agent 提醒模式 API 层完成`
  - `fix(reminder): agent.update 字段为 undefined 时转为 null，避免 SQL bind 错误`
  - `refactor: 移除 MCP 服务端，focus 全面转向 FIE 只读`

### 3.3 提交前自检

- 【必须】`npm run build:main` 与 `npm run build:renderer` 至少各自 tsc 通过（改哪个进程编哪个）。
- 【推荐】不提交 `.data/`、`dist/`、`release/`、`*.log`（已在 `.gitignore`，勿强改）。
- 【禁忌】提交含真实 API Key / Token 的配置或日志文件。

## 四、评审清单

### 4.1 代码评审要点（PR/提交对照）

**架构合规**
- [ ] 无插件间直接 import；跨模块通信走 `bus`。
- [ ] 对外能力只在 `api.ts` / `registerCommand`；无外部 import 插件内部实现。
- [ ] 渲染进程未直接 import 主进程/core/插件；只经 `window.assistant.*`。
- [ ] 新 bus 事件已在 `event-map.ts` 登记类型。
- [ ] 新 IPC 用 `defineInvoke/defineSend` 并加入 `ipc/index.ts` 列表，未在 `main/index.ts` 手写 `ipcMain.handle`。
- [ ] `window.assistant` 改动已同步 `shared/assistant-api.ts`。

**数据与错误**
- [ ] 写操作后有 `autoSave()`。
- [ ] SQL 绑定参数无 `undefined`（全部 `?? null`）。
- [ ] `stmt.free()` 在 `finally`。
- [ ] handler 异常已处理并记日志，未空吞。
- [ ] 建表逻辑在 `core:ready` 之后。

**质量**
- [ ] 命名符合 §1.1；文件顶部有职责注释。
- [ ] 无重复复制粘贴逻辑（S1 BUG-6：reminder "查最新一条" 复制 6+ 次，应抽 helper）。
- [ ] 无被注释掉的死代码、无 `console.log` 调试残留（正式日志走 logger）。

### 4.2 安全评审要点

- [ ] 日志/提交/上报**无** API Key、Token、完整用户输入、附件正文、base64。
- [ ] preload 只经 `contextBridge` 暴露最小 API，未暴露 `ipcRenderer`/Node API/任意命令执行。
- [ ] 终端 PTY、`cli.run` 等命令执行能力**未接入 AI 或远程内容驱动的调用链**（仅供用户手动操作）。
- [ ] CLI 走 loopback（`127.0.0.1`）无鉴权，未监听 `0.0.0.0`，未暴露到公网。
- [ ] 外部传入参数（CLI/IPC）在 handler 内做了基本校验与类型收敛。
- [ ] 焦点/提醒上报正文按隐私要求脱敏，未落地敏感原文。

## 五、EventBus 事件命名规范检查

### 5.1 规范

- 【必须】格式 `namespace:action`，冒号分隔。
- 【必须】`core:*` 为内核保留（`core:ready`/`core:plugins-loaded`/`core:plugin-activated`），**插件不得 emit `core:` 事件**。
- 【必须】其余以插件 id 为命名空间：`reminder:*`、`focus:*`、`knowledge-base:*`。
- 【推荐】生命周期事件统一 `<id>:activated` / `<id>:deactivated`；结果事件统一 `<id>:result` 或 `<id>:<verb>ed`（如 `focus:ingested`）。

### 5.2 现状核查结果（对照 `event-map.ts`）

| 检查项 | 结果 |
|--------|------|
| 所有事件均 `namespace:action` 格式 | ✅ 通过 |
| `core:*` 仅内核使用 | ✅ 通过 |
| 命名空间 == 插件 id | ✅ 通过（`knowledge-base:*` 等一致） |
| 生命周期事件齐全 | ✅ 通过（各插件 activated/deactivated 齐） |
| 事件均在 `AppEventMap` 登记 | ✅ 通过（运行时字符串场景走 `emitDynamic/onDynamic`，已隔离） |

- 【结论】EventBus 命名当前**无违规**。唯一注意点：动态事件（`emitDynamic`）仅限插件桥接等运行时字符串场景，业务代码一律用类型化的 `emit/on`，不得滥用 `emitDynamic` 绕过类型登记。

## 附：规则密度说明

本项目为**个人/小团队桌面工具**，规范刻意从简：
- 不强制单元测试覆盖率（`test` 仅在关键内核逻辑推荐）。
- 不引入重型 lint/CI 门禁，以「提交前 tsc 通过 + 评审清单自检」为主。
- 所有规则服务于**架构一致性**与**避免重复踩坑**，而非形式主义。规模扩大后再按需加密。
